# Cline Memory Bank — правила работы с проектом

Я — Cline, эксперт-разработчик. Моя память полностью сбрасывается между
сессиями. Это не ограничение — это причина вести идеальную документацию.

## 🔴 НЕ РАССЧИТЫВАЙ НА АВТОЗАГРУЗКУ ЭТОГО ФАЙЛА

Проверено фактически 05.10.2026: содержимое `.clinerules/memory-bank.md`
**не попало** в контекст сессии. Возможно, из-за того, что файл создан после
старта сессии; возможно, формат папки не поддерживается этой версией Cline.
Проверить наверняка можно только в новой сессии.

Поэтому основная инструкция продублирована в начале `README.md`
(раздел «⚡ Для ИИ-агента: начни отсюда») — README открывают всегда.

## 🔴 ОБЯЗАТЕЛЬНО в начале КАЖДОЙ задачи

Прежде чем что-либо делать, прочитай ВСЕ файлы из папки `memory-bank/`:

1. `activeContext.md` — **читать первым**, здесь текущий фокус и последние изменения
2. `projectbrief.md` — что это и границы проекта
3. `productContext.md` — зачем проект и сценарии
4. `systemPatterns.md` — архитектура, слои, поток данных
5. `techContext.md` — стек, команды, API, схема БД
6. `progress.md` — статус, что работает, известные ограничения

Это не опционально. Без чтения этих файлов я не понимаю проект.

Полные детали — в `README.md`, `ARCHITECTURE.md`, `TEST_REPORT.md`, `REVIEW.md`.
Memory Bank содержит **сжатую версию** и ссылки, а не копии.

⚠️ **Memory Bank может отставать от кода.** Если видишь расхождение — верь коду
и обнови нужный файл.

## 📐 Как я работаю

1. Прочитал Memory Bank → понял контекст
2. Прежде чем менять код — уточнил у пользователя, если что-то неясно
3. Делаю точечные правки, **не переписываю проект целиком**
4. Если узнал что-то новое о проекте — обновляю соответствующий файл Memory Bank
5. После значимых изменений — обновляю `activeContext.md` и `progress.md`
6. После **любых** правок запускаю `npm run test:all` (93 проверки)

## ⚠️ Известные грабли этого проекта

1. **`node --check` не гарантирует работоспособность.** Уже был случай: 2
   потерянные скобки сделали 22 из 24 функций клиента недоступными, а
   синтаксическая проверка проходила успешно. Ловится только тестами
   на поведение (`vm`-прогон, `logic-test.js`).
2. **Для CSS аналога `node --check` нет** — и 85 проверок это не поймали.
   Незакрытая скобка в `style.css` «съела» `.board` и `.cell`, и поле 3×3
   не отображалось вообще (был виден только текст). Перед правкой HTML/CSS
   запускай `node css-check.js` — он ловит баланс скобок и проверяет, что
   ключевые селекторы на верхнем уровне.
3. **`Node fetch` не понимает относительные пути** (`/api/games`). В тестах
   URL нужно превращать в абсолютный — иначе запрос молча уходит в никуда,
   а тест это замаскирует.
4. **Не использовать heredoc с многострочными Python-скриптами в `run_commands`** —
   шел ломает кавычки и портит файлы. Для правок использовать редактор или
   короткие однострочные команды.
5. **После вставок проверять порядок секций** (`grep -n '^## '`) — контент
   может встать не туда.
6. **Не оставлять фоновые `node server.js`** — они держат порт 3000 и ломают
   следующий `npm start`. После проверок: `pkill -f "node server.js"`.
7. **`timeout` в macOS — x86_64-бинарник** (Rosetta) и запускает дочерний
   `node` как x86_64, из-за чего нативный `better-sqlite3` падает с
   «incompatible architecture». Для фонового запуска использовать
   `(cmd & echo $! > /tmp/pid)` + `sleep` + `kill $(cat /tmp/pid)`.

## 🚫 Чего НЕ делать

- Не читать `node_modules/`, `*.sqlite`, `package-lock.json` — они в `.clineignore`
- Не переписывать рабочий код без причины
- Не молчать, если требования противоречат текущему коду — сообщить
- Не оставлять устаревшую информацию в Memory Bank
- Не дублировать README в Memory Bank — только сжатая суть и ссылки

## 📏 Размер файлов

Memory Bank должен оставаться компактным:

- `progress.md` ≤ 80 строк
- Остальные — ориентир 80–100 строк; `activeContext.md` и `systemPatterns.md`
  неизбежно длиннее: туда легли уроки из багов, терять их опаснее,
  чем превысить формат

Если файл разрастается — сжимай, переноси детали в код и README.

**Приоритет содержания:** правда о состоянии проекта важнее
соответствия лимитам. Устаревшая или выброшенная информация вреднее
длинного файла.
