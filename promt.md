# Задание: Разработка проекта "Крестики-нолики" с БД и мультиагентной разработкой

## 🎯 Цель
Создать полноценный веб-проект "Крестики-нолики" с сохранением результатов в базе данных,
используя методологию **Harness** — мультиагентный подход, где каждый этап выполняется
отдельной ролью (Architect → Developer → Tester → Reviewer → Documenter).

## 🛠️ Технологический стек
- **Backend:** Node.js + Express
- **База данных:** SQLite через `better-sqlite3` (синхронный API, без внешних сервисов)
- **Frontend:** чистый HTML + CSS + JavaScript (без фреймворков и CDN)
- **Запуск:** `npm install && npm start`
- **Порт:** 3000

## 💻 РОЛЬ 2: DEVELOPER (Разработчик)

**Твоя задача — реализовать то, что спроектировал Architect.**

Структура проекта:
```
tictactoe/
├── package.json
├── server.js          # Express-сервер + API-роуты
├── db.js              # Инициализация SQLite и запросы
├── database.sqlite    # Создаётся автоматически при первом запуске
├── public/
│   ├── index.html     # Меню + игровое поле
│   ├── style.css      # Стили
│   └── script.js      # Логика игры + fetch к API
└── README.md          # Создаётся Documenter'ом
```

### Требования к БД
Таблица `games`:
| Поле        | Тип      | Ограничения                              |
|-------------|----------|------------------------------------------|
| id          | INTEGER  | PRIMARY KEY AUTOINCREMENT                |
| player_name | TEXT     | NOT NULL, длина 1–30                     |
| result      | TEXT     | NOT NULL, CHECK IN ('win','lose','draw') |
| played_at   | DATETIME | DEFAULT CURRENT_TIMESTAMP                |

Индекс: `CREATE INDEX idx_played_at ON games(played_at DESC);`

### API-контракты
| Метод  | Путь         | Тело                          | Ответ                          |
|--------|--------------|-------------------------------|--------------------------------|
| GET    | /api/games   | —                             | `[{id, player_name, result, played_at}]` (последние 10) |
| POST   | /api/games   | `{player_name, result}`       | `{id, player_name, result, played_at}` |
| DELETE | /api/games   | —                             | `{deleted: N}`                 |

Коды ошибок: 400 (валидация), 500 (сервер).

### Требования к Frontend
**Экран 1 — Меню:**
- Заголовок "Крестики-нолики"
- Поле ввода имени игрока
- Кнопка "Начать игру"
- Таблица последних 10 игр (имя, результат, дата)
- Кнопка "Очистить историю"

**Экран 2 — Игра:**
- Поле 3×3
- Игрок = X, компьютер = O (простой ИИ: сначала выиграть, потом блокировать, потом центр/угол)
- Индикатор текущего хода
- Определение победы/ничьей
- Кнопка "Сыграть ещё" → возврат в меню
- После окончания партии — POST-запрос на сохранение

**Общие требования к коду:**
- Комментарии на русском
- Обработка ошибок (валидация, try/catch на fetch, показ уведомлений)
- Экранирование имени пользователя (защита от XSS)
- Приятный минималистичный CSS (тёмная тема)
- Адаптивность под мобильные

**После завершения — переходи к роли Tester.**

## 🧪 РОЛЬ 3: TESTER (Тестировщик)

**Твоя задача — проверить то, что написал Developer.**

Выполни:
1. **Статический анализ:**
   - Проверь, что все файлы созданы и соответствуют структуре
   - Проверь синтаксис (запусти `node -c server.js`, `node -c db.js`)
   - Проверь, что `package.json` содержит все зависимости и `start`-скрипт

2. **Проверка API вручную (curl):**
   - `GET /api/games` → пустой массив
   - `POST /api/games` с валидными данными → 200 + запись создана
   - `POST /api/games` с пустым именем → 400
   - `POST /api/games` с `result=bad` → 400
   - `POST /api/games` с именем из 100 символов → 400
   - `DELETE /api/games` → история очищена
   - `GET /api/games` после 15 записей → возвращает ровно 10

3. **Проверка фронтенда (чек-лист):**
   - [ ] Меню отображается при загрузке
   - [ ] Пустое имя → alert об ошибке
   - [ ] Игра запускается, поле кликабельно
   - [ ] X появляется в клетке, ход переходит к O
   - [ ] Компьютер делает ход
   - [ ] Победа определяется (горизонталь, вертикаль, диагональ)
   - [ ] Ничья определяется
   - [ ] После партии результат сохраняется и виден в меню
   - [ ] Имя с `<script>` не выполняется
   - [ ] Кнопка "Очистить историю" работает

4. **Отчёт:** создай файл `TEST_REPORT.md` с таблицей: тест | ожидание | результат | статус.

5. **Если найдены баги** — вернись к роли Developer, исправь, и снова вернись к Tester.
   Повторяй цикл, пока все тесты не пройдут.

**После прохождения всех тестов — переходи к роли Reviewer.**

## 🔍 РОЛЬ 4: REVIEWER (Ревьюер)

**Твоя задача — критически оценить качество кода и решения.**

Проверь:
1. **Читаемость:** понятны ли имена переменных/функций? Есть ли комментарии?
2. **Безопасность:**
   - SQL-инъекции (должны использоваться prepared statements в better-sqlite3)
   - XSS (экранирование имени)
   - Валидация на сервере, а не только на клиенте
3. **Архитектура:**
   - Нет ли дублирования кода?
   - Разделены ли слои (routes / db / logic)?
4. **UX:**
   - Понятно ли, что делать новому пользователю?
   - Есть ли обратная связь на действия (загрузка, ошибки)?
5. **Расширяемость:**
   - Легко ли добавить режим "2 игрока"?
   - Легко ли добавить рейтинг?

**Формат вывода:** раздел `## REVIEW.md` со списком замечаний уровня
`BLOCKER` / `MAJOR` / `MINOR` / `NICE-TO-HAVE`.

**Если есть BLOCKER или MAJOR** — вернись к Developer, исправь, прогони Tester заново.
**Если всё чисто** — переходи к Documenter.

## 🚦 ПОРЯДОК РАБОТЫ (Harness Pipeline)

```
[1] Architect  → план + ARCHITECTURE.md
       ↓ (жду подтверждения пользователя)
[2] Developer  → весь код проекта
       ↓
[3] Tester     → TEST_REPORT.md
       ↓ (если баги — назад к [2])
[4] Reviewer   → REVIEW.md
       ↓ (если замечания — назад к [2])
[5] Documenter → README.md
       ↓
[6] Финальный отчёт пользователю:
    - что сделано
    - как запустить
    - результаты тестов
    - известные ограничения
```

## ⚠️ Правила для всех ролей
- Работай **пошагово**: после каждой роли останавливайся и показывай результат
- Перед переходом к следующей роли **спрашивай подтверждение** у пользователя
- Не переписывай весь код с нуля при мелких правках — точечно исправляй
- Все комментарии в коде — на русском
- Всё, что можно проверить командой — проверяй командой, не угадывай
- Если чего-то не хватает в требованиях — **спроси**, не додумывай молча
