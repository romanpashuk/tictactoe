## 1. Обзор системы

Веб-приложение с сохранением результатов партий в SQLite.
Клиент — статические HTML/CSS/JS (без фреймворков и CDN).
Сервер — Node.js + Express, доступ к данным — только через синхронный `better-sqlite3`.

Ключевые архитектурные принципы:

| Принцип | Реализация |
|---|---|
| Слоистость | presentation → API → data, зависимости только «сверху вниз» |
| Синхронный доступ к данным | `better-sqlite3` (без callback/promise, нет гонок) |
| Валидация на сервере | клиентская валидация — только UX, не безопасность |
| Нет дублей валидации | одно место валидации — роуты `server.js` |
| Безопасность по умолчанию | prepared statements + экранирование на выводе |
| Простота запуска | `npm install && npm start`, БД создаётся автоматически |

## 2. Слоистая архитектура (ASCII)

```
┌──────────────────────────────────────────────────────────────────┐
│  PRESENTATION (клиент)                        public/            │
│                                                                  │
│  index.html ── Меню (имя, «Начать игру», таблица истории)         │
│      │                 Игровое поле 3×3                         │
│      ├── style.css ── тёмная тема, адаптивность                  │
│      └── script.js ── состояние игры, ИИ, fetch к API,           │
│                        экранирование имени (textContent)         │
│            │  HTTP/JSON (fetch)                                   │
└────────────┼─────────────────────────────────────────────────────┘
             │  GET/POST/DELETE /api/games
┌────────────▼─────────────────────────────────────────────────────┐
│  API / TRANSPORT (сервер)                     server.js          │
│                                                                  │
│  express.static('/')  ── раздача public/                        │
│  express.json()       ── парсинг тела запроса                     │
│  Роуты /api/games:   ── валидация, маппинг кодов ответа,        │
│                        обработка ошибок (try/catch → 500)        │
│  ── НЕ содержит SQL ──                                           │
└────────────┬─────────────────────────────────────────────────────┘
             │  вызовы функций
┌────────────▼─────────────────────────────────────────────────────┐
│  DATA (доступ к данным)                     db.js                │
│                                                                  │
│  initDb()         ── открытие БД, CREATE TABLE/INDEX (идемпот.)  │
│  listGames(limit) ── SELECT ... ORDER BY played_at DESC LIMIT ?   │
│  createGame()     ── INSERT c prepared statement                  │
│  clearGames()     ── DELETE FROM games; возвращает count         │
│  ── единственное место, где живёт SQL ──                          │
└────────────┬─────────────────────────────────────────────────────┘
             │
┌────────────▼─────────────────────────────────────────────────────┐
│  STORAGE                                  database.sqlite         │
│  Таблица games (см. раздел 3). Создаётся автоматически.          │
└──────────────────────────────────────────────────────────────────┘
```

Правила зависимостей:
- `script.js` знает только про HTTP-контракт (не про SQL).
- `server.js` знает только про функции `db.js` (не про SQL).
- `db.js` ничего не знает про Express и HTTP.
- Бизнес-логика игры (правила, ИИ) живёт **на клиенте**; сервер валидирует
  только форму записи результата.

## 3. Схема базы данных

### 3.1 Таблица `games`

| Поле | Тип | Ограничения | Назначение |
|---|---|---|---|
| `id` | INTEGER | `PRIMARY KEY AUTOINCREMENT` | Уникальный идентификатор записи |
| `player_name` | TEXT | `NOT NULL`, `CHECK(length(trim(player_name)) BETWEEN 1 AND 30)` | Имя игрока |
| `result` | TEXT | `NOT NULL`, `CHECK(result IN ('win','lose','draw'))` | Итог партии с точки зрения игрока |
| `played_at` | DATETIME | `DEFAULT CURRENT_TIMESTAMP` | Время окончания партии (UTC, `YYYY-MM-DD HH:MM:SS`) |

### 3.2 DDL

```sql
CREATE TABLE IF NOT EXISTS games (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  player_name TEXT    NOT NULL
                      CHECK(length(trim(player_name)) BETWEEN 1 AND 30),
  result      TEXT    NOT NULL
                      CHECK(result IN ('win', 'lose', 'draw')),
  played_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_played_at ON games(played_at DESC);
```

Дополнительно при инициализации: `PRAGMA journal_mode = WAL;` — устойчивость
к параллельным запросам.

### 3.3 Индексы

| Индекс | Поля | Зачем |
|---|---|---|
| `idx_played_at` | `played_at DESC` | Ускорение `ORDER BY played_at DESC` в `listGames()` — основной запрос приложения |

### 3.4 Поведение при недоступной БД

- При старте `initDb()` обёрнут в `try/catch`. При ошибке: понятное сообщение
  в stderr и `process.exit(1)` (fail-fast — нельзя играть без сохранения результатов).
- В рантайме падение запроса к БД → JSON-ответ `500`
  `{ "error": "Ошибка базы данных" }`, реальная причина логируется в stderr.

## 4. API-контракты

Базовый URL: `http://localhost:3000`. Формат обмена — JSON
(`Content-Type: application/json`). Тело любой ошибки: `{ "error": "<текст на русском>" }`.

### 4.1 `GET /api/games`

| | |
|---|---|
| **Метод** | GET |
| **Путь** | `/api/games` |
| **Тело запроса** | — |
| **Успех** | `200 OK` |
| **Тело ответа** | Массив **не более 10** объектов, `played_at` DESC |

```json
[
  {
    "id": 12,
    "player_name": "Алиса",
    "result": "win",
    "played_at": "2026-10-05 14:03:21"
  }
]
```

Пустая история → `200 OK` и `[]` (не 404).

### 4.2 `POST /api/games`

| | |
|---|---|
| **Метод** | POST |
| **Путь** | `/api/games` |
| **Тело запроса** | `{ "player_name": string, "result": "win"\|"lose"\|"draw" }` |
| **Успех** | `201 Created` |
| **Тело ответа** | Созданная запись `{ id, player_name, result, played_at }` |

### 4.3 `DELETE /api/games`

| | |
|---|---|
| **Метод** | DELETE |
| **Путь** | `/api/games` |
| **Тело запроса** | — |
| **Успех** | `200 OK` |
| **Тело ответа** | `{ "deleted": 12 }` (0, если история пуста) |

### 4.4 Коды ошибок

| Код | Когда | Пример тела |
|---|---|---|
| `400 Bad Request` | Невалидный JSON, отсутствует поле, `player_name` не строка, пустая/пробельная строка, длина > 30, неизвестный `result` | `{"error":"Имя игрока: от 1 до 30 символов"}` |
| `404 Not Found` | Несуществующий путь `/api/*` | `{"error":"Не найдено"}` |
| `500 Internal Server Error` | Необработанная ошибка, в т.ч. сбой БД | `{"error":"Внутренняя ошибка сервера"}` |

### 4.5 Правила валидации (единое место — `server.js`)

1. `player_name`: приведение к строке, `trim()`, длина **после trim** — 1..30.
   В БД сохраняется trim-версия.
2. `result`: строго один из `'win' | 'lose' | 'draw'`.
3. Порядок проверок: тип → обязательность → длина → допустимое значение.
4. SQL-инъекции невозможны: только prepared statements (`db.prepare(...).run/get/all`).

## 5. Пользовательские сценарии (User Stories)

### US-1. Начало игры
**Как** новый пользователь, **я хочу** ввести своё имя и начать игру,
**чтобы** играть против компьютера от своего имени.
- Меню отображается при загрузке страницы.
- Пустое имя → `alert` с понятной ошибкой, игра не начинается.
- Имя длиннее 30 символов → ошибка, кнопка не запускает игру.
- Клик «Начать игру» → экран игры, поле 3×3 кликабельно.

### US-2. Партия против компьютера
**Как** игрок, **я хочу** играть за `X` против компьютера за `O`,
**чтобы** игра была интересной.
- Клик по клетке → в клетке появляется `X`.
- Ход автоматически переходит к компьютеру (`O`) с небольшой задержкой.
- Индикатор «Ваш ход» / «Ход компьютера» обновляется.
- Клик по занятой клетке или во время хода компьютера игнорируется.
- Победа (горизонталь / вертикаль / диагональ) и ничья определяются и объявляются.
- После завершения партии поле блокируется, показывается итог.

### US-3. Автосохранение результата
**Как** игрок, **я хочу**, чтобы результат сохранялся сам,
**чтобы** не терять статистику.
- После «Победа» / «Поражение» / «Ничья» клиент автоматически шлёт `POST /api/games`.
- При успехе — уведомление «Результат сохранён».
- При ошибке сети/сервера — уведомление с ошибкой (сохранение можно повторить).

### US-4. Просмотр истории
**Как** игрок, **я хочу** видеть историю своих и чужих игр,
**чтобы** понимать прогресс.
- При открытии/возврате в меню выполняется `GET /api/games`.
- Таблица показывает: имя, результат (человекочитаемый текст), дата.
- Показываются последние 10 записей; если записей нет — «История пока пуста».
- Имя `<script>alert(1)</script>` отображается как текст, не исполняется.

### US-5. Очистка истории
**Как** игрок, **я хочу** очистить историю,
**чтобы** начать статистику с нуля.
- Клик «Очистить историю» → `confirm()` → `DELETE /api/games`.
- После успеха таблица пуста, уведомление «История очищена (N)».

### US-6. Возврат в меню
**Как** игрок, **я хочу** начать новую партию,
**чтобы** играть снова.
- Кнопка «Сыграть ещё» возвращает в меню, история подгружается заново.
- Сохранённое имя подставляется в поле ввода.

## 7. Граничные случаи и решения

### 7.1 Валидация имени
| Случай | Поведение |
|---|---|
| Пустое имя `""` | Клиент: `alert("Введите имя")`, игра не начинается. Сервер: `400`. |
| Только пробелы `"   "` | Как пустое имя (проверка после `trim()`). |
| Имя из 1 символа | Допустимо. |
| Имя из 30 символов | Допустимо (граница включена). |
| Имя из 31+ символов (в т.ч. 100) | Клиент: подсветка ошибки. Сервер: `400`. |
| Имя отсутствует / `null` / число / объект | Сервер: `400`. |
| `result = "bad"` или отсутствует | Сервер: `400`. |
| Тело запроса — невалидный JSON | Сервер: `400` (перехват ошибки парсера). |
| Лишние поля в теле | Игнорируются. |

### 7.2 XSS и безопасность вывода
| Случай | Решение |
|---|---|
| `<script>alert(1)</script>` в имени | Никогда не используется `innerHTML` для данных: только `textContent`. |
| Попытка SQL-инъекции через API | Prepared statements в `better-sqlite3` — инъекция невозможна. |
| Ошибка сети (`fetch` reject) | `try/catch` → уведомление пользователю, сервер не падает. |
| Некорректный JSON в ответе | Проверка `res.ok` до `res.json()`. |

### 7.3 Недоступность БД
| Случай | Решение |
|---|---|
| Файл БД недоступен на старте | Сообщение в stderr + `process.exit(1)`. |
| БД недоступна в рантайме | `500` в JSON, лог реальной причины в stderr, приложение не падает. |
| Повреждённый `database.sqlite` | Рекомендация в README: удалить файл и перезапустить. |

### 7.4 Игровая логика
| Случай | Решение |
|---|---|
| Клик по занятой клетке | Ход игнорируется. |
| Клик во время хода компьютера | Поле временно заблокировано (флаг `isThinking`). |
| Победа на последнем ходу | Проверка победы выполняется **до** проверки ничьей. |
| Поле заполнено, победителя нет | `draw` → сохранение. |
| Игра окончена до хода компьютера | Ход компьютера не делается. |
| ИИ не нашёл ход | Фолбэк — первый свободный индекс (страховка от «зависания»). |
| Быстрые повторные клики | Защита флагом состояния + проверкой результата партии. |
| Уход со вкладки / resize | Не влияет: состояние в памяти страницы. |

### 7.5 История
| Случай | Решение |
|---|---|
| Записей 0 | `200` + `[]`, UI: «История пока пуста». |
| Записей 15 | Возвращаются ровно 10 последних (`LIMIT 10`). |
| Одинаковые `played_at` | Стабильная сортировка: вторичный ключ `id DESC`. |
| DELETE на пустой БД | `200` + `{"deleted": 0}`, без ошибки. |
| Очистка без подтверждения | Клиент спрашивает `confirm()`. |

## 8. Стратегия тестируемости (вход для роли Tester)

- Чистый вход через `curl` — все сценарии раздела 4 проверяемы без UI.
- Инициализация БД идемпотентна (`IF NOT EXISTS`), сервер можно перезапускать.
- `GET /api/games` детерминирован: ≤10 записей, стабильная сортировка.
- Валидация продублирована в `CHECK`-ограничениях БД — «эшелонированная защита».

## 9. Архитектурные решения (ADR-лайт)

| # | Решение | Альтернатива | Почему |
|---|---|---|---|
| 1 | `better-sqlite3` (синхронный) | `sqlite3` / ORM / внешняя БД | Нет внешних сервисов, нет гонок, простой `npm start` |
| 2 | Валидация в `server.js` + `CHECK` в БД | Только клиент | Клиент недоверенный; сервер — источник истины |
| 3 | SQL только в `db.js` | SQL в роутах | Разделение слоёв, тестируемость, ревью |
| 4 | Один `index.html` с двумя состояниями | SPA с роутингом | Нет зависимостей, достаточно для задачи |
| 5 | `textContent` для имени | `innerHTML` | Защита от XSS по умолчанию |
| 6 | `DELETE /api/games` очищает всю историю | DELETE по id | Соответствует кнопке «Очистить историю» из ТЗ |
| 7 | Лимит 10 задаётся в SQL (`LIMIT`) | Фильтрация в JS | Меньше трафика, работает с индексом |

## 10. Критерии готовности к этапу Developer

- [ ] `package.json` с `express`, `better-sqlite3`, скриптом `start`
- [ ] `db.js` — схема + 3 функции данных, только prepared statements
- [ ] `server.js` — 3 роута по контрактам раздела 4, коды 400/404/500
- [ ] `public/index.html` — меню + поле 3×3
- [ ] `public/script.js` — правила, ИИ, fetch, экранирование, уведомления
- [ ] `public/style.css` — тёмная тема, адаптивность
- [ ] Комментарии на русском
- [ ] `npm install && npm start` поднимает сервер на 3000, БД создаётся сама
- `db.js` — единственное место с SQL; `CHECK`-ограничения как второй рубеж.
- `server.js` — HTTP-слой: маршруты, HTTP-валидация, коды ответов, логирование. Без правил игры.
- `public/script.js` — клиентская логика: правила, ИИ, рендеринг, fetch. Без SQL.
