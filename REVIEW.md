## 2. Безопасность

### 2.1 SQL-инъекции — ✅ ЗАЩИЩЕНО

Весь SQL сосредоточен в `db.js` (проверено: в `server.js` нет ни одного SQL-запроса).

| Место | Как сделано | Оценка |
|---|---|---|
| `listGames()` | `prepare('SELECT ... LIMIT ?')` + `query.all(safeLimit)` | ✅ параметризован |
| `createGame()` | `prepare('INSERT ... VALUES (?, ?)')` + `query.run()` | ✅ параметризован |
| `clearGames()` | `prepare()` без подстановки строк | ✅ безопасно |
| чтение вставленной записи | `prepare('... WHERE id = ?')` + `.get(lastInsertRowid)` | ✅ параметризован |

**Проверено фактически (T14/T15 в TEST_REPORT.md):**
- `x'; DROP TABLE games;--` сохранён как текст, таблица цела, `GET` → `200`;

Дополнительный плюс: `limit` приводится к `Number.isInteger(...) > 0`
(`db.js:80`) — в `LIMIT` попасть может только число.

| Аспект | Оценка |
|---|---|

**MINOR-2. `server.js` импортирует константы из слоя данных.**
`db.ALLOWED_RESULTS` (`server.js:66,69`) и `db.HISTORY_LIMIT` (`server.js:84`)
берутся из модуля данных. Формально это создаёт связь API-слоя от слоя данных,
хотя `db.js` документирован как «модуль, ничего не знающий про HTTP».
На практике связь безопасна (это просто данные), но нарушает декларируемое
разделение.
**Рекомендация:** вынести доменные константы в отдельный `constants.js`,
который импортируют и `server.js`, и `db.js`.

**Положительный момент.** `getDb()` лениво инициализирует БД, если `initDb()`
не вызывался (`db.js:65-71`). Это делает модуль устойчивым к неправильному
порядку инициализации — типичная ошибка в таких проектах здесь не проявилась.

## 5. Расширяемость

### 5.1 Режим «2 игрока»

Оценка: **сложно, требует переработки**.

| Что мешает | Пояснение |
|---|---|
| Игра в `script.js` | Правила и ходы живут на клиенте, сервер о них не знает |
| Схема `result` | Нет сущности «партия» с участниками; только «имя + результат» |
| Автосохранение | Один игрок → одно поле `player_name` |

Потребуется: таблица `games` с полями `x_name`, `o_name`; ход человека вместо
таймера `computerMove`; новая ветка в `saveGameResult`. Ядро (`db.js`,
`server.js`) переживёт это без изменений — **разделение слоёв свою задачу
выполнило**.

### 5.2 Рейтинг

Оценка: **умеренно сложно**. Потребуется запрос «посчитать победы по имени» и
вычисление процента побед. `db.js` расширяется новой функцией (`getStats(name)`),
`server.js` — новым маршрутом `GET /api/stats`. Клиент покажет колонку.
Архитектура позволяет добавить это без переписывания.

**Вывод:** архитектура не препятствует расширению, но игровая логика целиком на
клиенте делает режим «2 игрока» нетривиальным. Это осознанный компромисс,
зафиксированный в ARCHITECTURE.md (ADR-4, ADR-7).

### MINOR-5. `finishGame()` не защищена от повторного вызова

Проверено скриптом `review-probe.js`: два последовательных вызова
`evaluateGameState()` приводят к **двум** POST-запросам (счётчик показал `1 → 2`).

Однако в реальном пользовательском сценарии путь недостижим: `finishGame()`
ставит `isGameActive = false`, а `handleCellClick()` первым делом проверяет
`if (!isGameActive) return;`. Это подтверждено пробой: клики после победы
добавили `+0` POST.

**Вывод:** реальной двойной записи нет, но защита держится на «дистанции»
(в `handleCellClick`), а не на самой `finishGame`. Это хрупко: любая будущая
функция, вызывающая `finishGame` напрямую, создаст дубликаты.

**Рекомендация (одна строка, устраняет класс проблемы целиком):**
```js
function finishGame(result, winningLine) {
  if (!isGameActive) return; // уже завершена — защита от повторного сохранения
  isGameActive = false;
  ...
}
```

## 9. Заключение

Код написан аккуратно и соответствует заявленной архитектуре:

- **безопасность** — оба вектора атаки (SQL-инъекция, XSS) закрыты и проверены фактически, а не деклативно;
- **разделение слоёв** — соблюдено, SQL изолирован в `db.js`, что позволяет безболезненно расширять проект;
- **валидация** — тройная, сервер является источником истины;
- **обработка ошибок** — единообразная, внутренние детали не утекают наружу;
- **тестируемость** — 64 автопроверки, включая сквозной сценарий с реальной БД.

Критических замечаний нет. Все 5 замечаний MINOR и 6 NICE-TO-HAVE — улучшения
качества, а не исправления дефектов: приложение работает корректно во всех
проверенных сценариях.
